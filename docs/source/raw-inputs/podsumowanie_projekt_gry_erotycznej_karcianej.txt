PODSUMOWANIE KONTEKSTU PROJEKTU: EROTYCZNA GRA KARCIANA WEB/PWA

Cel projektu
------------
Użytkownik chce stworzyć prostą grę towarzyską/karcianą, potencjalnie erotyczną/pikantną, podobną ideowo do Taboo, gier imprezowych lub gier dla par. Gra ma działać przede wszystkim na iPhonie, ale najlepiej również na Androidzie i komputerze. Użytkownik zna Javę, React i TypeScript, więc preferowany stack powinien wykorzystywać te technologie.

Najważniejsza decyzja technologiczna
------------------------------------
Najbardziej sensowna ścieżka dla pierwszej wersji to:

Frontend:
- React
- TypeScript
- Vite
- PWA, czyli Progressive Web App

Backend:
- Java 21
- Spring Boot 3
- WebSocket / STOMP albo prosty WebSocket
- opcjonalnie PostgreSQL w późniejszej fazie
- opcjonalnie Redis w późniejszej fazie, jeśli pokoje gry mają działać na wielu instancjach backendu

Dlaczego PWA
------------
PWA to strona internetowa, która zachowuje się prawie jak aplikacja. Na iPhonie użytkownik otwiera ją w Safari, a potem może dodać ją do ekranu początkowego przez:

Udostępnij -> Dodaj do ekranu początkowego

Po dodaniu pojawia się ikonka jak dla normalnej aplikacji. Aplikacja może działać pełnoekranowo, zapisywać dane lokalnie i częściowo działać offline.

PWA pasuje do tego projektu, bo:
- nie wymaga App Store,
- nie wymaga review Apple,
- jest dobra dla gry karcianej / quizowej / imprezowej,
- działa na iPhonie, Androidzie, komputerze i tablecie,
- można ją pisać w React + TypeScript,
- backend może być w Javie,
- można łatwo aktualizować treści kart bez wydawania nowej aplikacji.

Ograniczenia PWA
----------------
PWA na iPhonie ma też ograniczenia:
- nie ma pełnego dostępu do wszystkich natywnych funkcji iOS,
- Bluetooth w PWA na iOS jest praktycznie słabym pomysłem,
- użytkownik musi ręcznie dodać aplikację do ekranu początkowego,
- cache/storage nie powinien być traktowany jak w pełni trwały dysk,
- iOS może ubijać aplikację w tle, jeśli zużywa zbyt dużo zasobów.

App Store a treści erotyczne
----------------------------
Apple ma ograniczenia dotyczące aplikacji z treściami seksualnymi. Lekki flirt, sugestywne pytania, gra dla par, romantyczne/odważniejsze wyzwania mogą potencjalnie przejść przez App Store, ale bardziej dosłowne treści seksualne, pornograficzne opisy, nagość lub aplikacja nastawiona głównie na pobudzenie erotyczne mogą zostać odrzucone.

Dla pikantniejszej wersji gry najrozsądniejsza jest wersja web/PWA poza App Store.

Możliwa strategia produktowa:
- pełna/pikantna wersja jako PWA/web,
- ewentualnie łagodniejsza wersja w App Store w przyszłości.

Bluetooth vs serwer
-------------------
Gra na kilka urządzeń przez Bluetooth na iPhonie jest technicznie możliwa tylko w bardziej natywnych rozwiązaniach, np. React Native z BLE, ale dla tego projektu jest to zbyt skomplikowane i nieopłacalne.

Lepsza opcja multiplayer:
- pokoje gry tworzone na backendzie,
- dołączanie przez kod pokoju lub link,
- synchronizacja gry przez WebSocket.

Przykładowy model działania multiplayer:
1. Host tworzy pokój.
2. Backend generuje kod, np. HOT-482.
3. Inni gracze wpisują kod lub klikają link.
4. Backend synchronizuje stan gry:
   - aktualną rundę,
   - aktualną kartę,
   - timer,
   - punkty,
   - drużyny,
   - gracza aktywnego,
   - poziom ostrości.

Proponowane tryby gry
---------------------
1. Tryb jednego telefonu:
   - jeden iPhone leży na stole,
   - gracze przekazują sobie telefon,
   - aplikacja losuje karty,
   - zapisuje punkty i rundy lokalnie.

2. Tryb dla pary:
   - jedna osoba tworzy pokój,
   - druga dołącza kodem,
   - obie osoby widzą zsynchronizowane karty/zadania.

3. Tryb imprezowy:
   - kilka telefonów,
   - drużyny,
   - punkty,
   - timer,
   - różne poziomy ostrości.

4. Tryb offline:
   - użytkownik pobiera wybraną talię,
   - gra może działać bez internetu na jednym urządzeniu.

Poziomy ostrości kart
---------------------
Warto podzielić treści na poziomy, np.:

Soft:
- flirt,
- zabawne pytania,
- komplementy,
- lekkie wyzwania.

Medium:
- bardziej osobiste pytania,
- romantyczne/odważniejsze zadania,
- gra dla par.

Hot:
- treści 18+,
- pikantniejsze pytania i wyzwania,
- najlepiej tylko w wersji web/PWA, nie w App Store.

Custom:
- użytkownik może tworzyć własne prywatne karty.

Ważna uwaga: publiczne talie użytkowników, czat, komentarze, profile i losowy matchmaking zwiększają ryzyko moderacyjne oraz prawne. Na start lepiej zrobić prywatne talie i prywatne pokoje bez publicznego UGC.

Zasoby, grafiki i cache
-----------------------
Nie należy pobierać wszystkich grafik kart przy każdym starcie gry.

Zalecany model:
- przy starcie pobrać tylko app shell: HTML/CSS/JS, podstawowe ikonki, logo, tła, manifest PWA,
- pobrać listę talii i metadane,
- pobrać teksty kart aktywnej talii,
- grafiki kart pobierać leniwie, dopiero gdy są potrzebne,
- w tle można preloadować kilka kolejnych grafik,
- pobrane grafiki trzymać w cache.

Gdzie trzymać dane lokalnie:
- Cache API: JS, CSS, HTML, fonty, grafiki, ikony, assety,
- IndexedDB: talie, teksty kart, stan gry, ustawienia, własne karty użytkownika,
- localStorage: tylko drobne ustawienia, np. wybrana talia, motyw, ostatni kod pokoju.

Nie należy trzymać dużych grafik w localStorage ani jako base64 w JSON-ie.

Format grafik
-------------
Zalecane formaty:
- WebP lub AVIF dla grafik kart i tła,
- SVG dla ikon i prostych elementów UI,
- PNG tylko tam, gdzie jest naprawdę potrzebny.

Rekomendowane rozmiary:
- miniaturka karty: 300-600 px szerokości,
- pełna grafika karty: 800-1200 px szerokości,
- jedna grafika najlepiej ok. 50-200 KB.

Przykładowe budżety:
- 100 kart x 100 KB = ok. 10 MB,
- 500 kart x 100 KB = ok. 50 MB,
- 1000 kart x 100 KB = ok. 100 MB.

To jest rozsądne dla PWA. Trzeba unikać sytuacji typu 1000 kart po 2 MB, bo to da 2 GB assetów i będzie bardzo złe dla iPhone'a.

Ograniczenia pamięci
--------------------
Trzeba rozróżnić RAM i storage/cache.

RAM:
- PWA działa w WebKit/Safari,
- nie ma prostego gwarantowanego limitu,
- iOS może ubić aplikację, gdy zużywa za dużo pamięci,
- bezpiecznie jest trzymać w RAM tylko aktualną kartę, kilka następnych, stan gry i podstawowe assety.

Storage/cache:
- nowoczesne iOS/Safari mają lepsze limity niż kiedyś,
- PWA dodane do ekranu początkowego może mieć większą quotę storage,
- mimo tego cache nie jest gwarantowany na zawsze,
- system może usunąć dane przy braku miejsca,
- aplikacja powinna umieć ponownie pobrać zasoby.

Bezpieczne założenie projektowe:
- MVP powinno dobrze działać przy 50-200 MB cache,
- pojedyncza talia offline: 20-80 MB,
- kilka talii offline: 100-300 MB,
- powyżej 500 MB trzeba już bardzo uważać i dodać zarządzanie pobranymi zasobami.

Proponowane endpointy backendu
------------------------------
Na MVP backend może serwować API i statyczne grafiki:

GET /api/decks
GET /api/decks/{deckId}
GET /api/decks/{deckId}/cards
GET /assets/cards/{cardId}.webp
WS  /ws/game

W przyszłości lepiej rozdzielić:
- Spring Boot: logika gry, pokoje, WebSocket, użytkownicy, płatności, talie,
- CDN / S3 / Cloudflare R2: grafiki, audio, paczki offline.

Przykładowy model karty
-----------------------
TypeScript:

type Card = {
  id: string;
  deckId: string;
  title: string;
  text: string;
  level: 'soft' | 'medium' | 'hot';
  imageUrl?: string;
  imageVersion?: string;
};

Nie należy robić:
{
  "id": "card-1",
  "image": "data:image/png;base64,..."
}

Lepiej:
{
  "id": "card-1",
  "imageUrl": "/assets/cards/card-1.webp",
  "imageVersion": "v3"
}

Wersjonowanie talii i assetów
-----------------------------
Każda talia powinna mieć wersję, np.:

{
  "deckId": "party-hot",
  "version": 12,
  "cardsVersion": 8,
  "assetsVersion": 4
}

Przy starcie frontend pyta backend, czy ma aktualną wersję talii. Jeśli tak, używa lokalnych danych. Jeśli nie, pobiera tylko zmienione karty i assety.

Rekomendowany plan MVP
----------------------
Etap 1:
- React + TypeScript + Vite + PWA,
- gra lokalna na jednym telefonie,
- kilka talii,
- poziomy ostrości,
- timer,
- punkty,
- podstawowy cache,
- brak kont użytkownika.

Etap 2:
- edytor własnych prywatnych kart,
- zapisywanie talii lokalnie w IndexedDB,
- opcja "Pobierz talię offline".

Etap 3:
- Java Spring Boot backend,
- WebSocket,
- pokoje gry,
- dołączanie kodem,
- synchronizacja rund, kart, timerów i punktów.

Etap 4:
- konta opcjonalne,
- płatne talie,
- płatności przez Stripe/PayU/Przelewy24, po sprawdzeniu regulaminów dla adult content,
- ewentualna łagodniejsza wersja App Store.

Najważniejsze decyzje
---------------------
1. Nie pisać aplikacji iOS w Javie.
2. Użyć React + TypeScript jako frontend.
3. Użyć PWA, żeby działało na iPhonie bez App Store.
4. Użyć Javy/Spring Boot jako backendu.
5. Multiplayer robić przez serwer i WebSocket, nie Bluetooth.
6. Pikantną wersję prowadzić przez web/PWA, nie przez App Store.
7. Grafiki kart ładować leniwie i cache'ować.
8. Teksty kart i stan gry trzymać w IndexedDB.
9. Dodać poziomy ostrości i prywatne talie.
10. Unikać publicznego UGC na start, bo wymaga moderacji i zwiększa ryzyko.

Krótka rekomendacja końcowa
---------------------------
Najlepszy stack dla tego projektu:

Frontend:
React + TypeScript + Vite + PWA + IndexedDB/Dexie + Cache API

Backend:
Java 21 + Spring Boot 3 + WebSocket + PostgreSQL później + Redis później

Dystrybucja:
PWA otwierane na iPhonie przez Safari i dodawane do ekranu początkowego.

To pozwala stworzyć pikantną grę karcianą bez ograniczeń App Store, z możliwością działania na wielu urządzeniach przez backend i bez konieczności pisania natywnej aplikacji iOS.
